| D12 | 2026-09-19 | The tuning run uses **`workers: 3`, pinned to logical CPUs 2, 4 and 6**. | 4 workers (one per physical core); unpinned workers; 1 worker. | Measured, not assumed: on the 1800-client instance each of 2 or 3 pinned workers does 106 % of the iterations a single worker does alone in the same 60 s, and each of 4 drops to 77 %. Four workers would buy nothing in total (3.06x vs 3.17x) and would change what "10 minutes" means to the solver. Core 0 stays free for the OS, the driver and the dashboard. Baseline and candidates run under the same setting. |
| D13 | 2026-09-20 | Measurements and the tuning run execute from a **detached worktree** (`runs/wt`), not from the checkout I develop in. | Being careful. | Being careful already failed once: switching branches removed the benchmark's files under a running measurement. | D14 | 2026-09-20 | Features are **stacked** PRs against `master` (each branch contains the ones below it) and every one carries a compare link that shows its own diff. | One PR per feature cut from master independently; one big PR. | The features build on each other's code (the dashboard draws the status document, which reads the event log, ...); independent branches would not even import. One big PR is not reviewable. The cost is that the GitHub diff of a stacked PR shows the stack, hence the explicit link. |
| D15 | 2026-09-20 | A per-instance stage combines instances as **percent of the baseline per instance** by default (`normalize: baseline`); the plain mean is opt-in and stays available as `<objective>_raw`. | Plain mean by default. | The benchmark's instances differ by 3x in size and more in cost; a plain mean lets the largest decide. Which default is less harmful when wrong: a plain mean fails *silently* (the search optimises two instances out of ten), normalisation fails *loudly* (a baseline value <= 0 stops with a message naming `normalize: none`). The divisor is fixed per run, so noise in the baseline run moves where 100 lies, never the ranking. |
| D16 | 2026-09-20 | `retries` defaults to **0**; the tuning setup sets 1. | Defaulting to 1. | A retry doubles the cost of a deterministic failure, and the most expensive failure -- a timeout -- is usually deterministic. The user who knows their solver crashes at random opts in. |
| D17 | 2026-09-20 | `--time-limit` in the benchmark bounds the whole `pyvrp.solve` call; instance loading and matrix construction are outside the limit and reported as `load_s`. | Bounding the process. | PyVRP's own `MaxRuntime` starts its clock after the first two iterations, which on a 3000-client instance is seconds; a private deadline fixed before the call is the honest reading of "10 minutes wall-clock per instance". Load time is identical for every configuration, so it carries no tuning signal; the stage `timeout` (process level) still bounds it. |

| D20 | 2026-09-20 | **While the tuning run is going, nothing else runs on this machine -- not even pinned to the free core.** Tests of new work go to CI (every PR runs the full suite there); locally I only write. The run `pyvrp-hard-1` is *kept* despite a contaminated first screening, and the contamination is reported. | (a) Running my test suites pinned to logical CPUs 0-1 at below-normal priority, which is what I did for the first 15 minutes of generation 1. (b) Restarting the run. | Evidence: `g001-c0003` differs from the defaults by `penalty_decrease` 0.9 -> 0.896 and did 19-33 % fewer iterations than the baseline on the same instances and time limit (t01: 93.7 vs 115.0 it/s; t07: 37.2 vs 55.9); all six local-step children of generation 1 were slower, by 15-30 %. The baseline's own rates were flat for its 42 minutes (t01 115 -> 117 it/s, t04 71 -> 71, t07 56 -> 57), so it is not thermal drift; and every one of those screening runs overlapped with my pinned test runs on core 0. That matches the earlier throughput measurement (a fourth busy core: 77 % each): on this 28 W laptop CPU the cores share one power budget, so *pinning protects the solver's cores from being scheduled on, not from being slowed down*. Consequence for the run: the eight screening scores of generation 1 are biased by roughly +2 to +5 % (worse); their ranking among each other, which is all the promotion rule uses, is affected much less, and no full-stage evaluation is affected. Restarting would cost an hour and buy eight cleaner numbers out of ~130. Consequence for the framework: a time-limited evaluation should record how busy the machine was (follow-up: host CPU load per evaluation in the event log, flagged on the dashboard -- friction item O-18). |
